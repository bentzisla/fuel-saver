# 0.7 — OBD link robustness (stream: obd-link)

## Problems

1. **Silent dongle hangs the engine and can freeze the UI (high).** If the adapter stopped
   answering while the Bluetooth link stayed up, the engine waited forever. `stop()` then did
   `runBlocking { job.cancelAndJoin() }` on the main thread (service `onDestroy`, Stats
   disconnect/reset), which could never finish, so the app froze until an ANR.
2. **"The OBD connects only after unplugging and re-plugging the dongle" (high, reported by
   the user).** Evidence from the phone: `last_obd_error = "INIT TIMEOUT"`, and the adapter is
   `00:00:00:33:33:33`, the common cheap "OBDII" ELM327 v1.5 clone. These clones accept only
   one RFCOMM link, are slow to let go of an old one, and often answer `ATZ` late or with
   garbage.

## Root cause analysis

### Certain (read directly from the code)

| # | Finding | Effect |
|---|---------|--------|
| C1 | `applySoTimeout` read `BluetoothSocket.mSocket` and cast it to `java.net.Socket`. In AOSP that field is an `android.net.LocalSocket`, so the cast always gave `null` and **no read timeout was ever set**. Lint flagged it as `DiscouragedPrivateApi`. | `readUntilPrompt` blocked forever on a silent adapter. |
| C2 | `sendCommand` did its blocking read inside `withContext(Dispatchers.IO)`. Cancelling the coroutine does not interrupt that read, and `withContext` waits for its block to finish. So `withTimeoutOrNull` in `sendInitCommand` **could not fire on time**. When the reply finally came, *after* the 600 ms / 3 s deadline, it was **thrown away and reported as `INIT TIMEOUT`**, and the socket was then closed. Run-loop polls had no timeout at all. | A dongle that was **slow but working** got `INIT TIMEOUT`. A **silent** dongle stayed in "Connecting" forever. |
| C3 | Every init failure was reported as `INIT TIMEOUT`: a write failure (`""`), immediate EOF and an `IOException` in `readUntilPrompt` all looked the same. | The persisted `INIT TIMEOUT` does not prove the adapter was slow. It may mean the RFCOMM link was dead or half-open. |
| C4 | `ObdEngine.stop()` used `runBlocking` + `cancelAndJoin`, called on the main thread. | UI freeze or ANR whenever a read hung (C1). Even when nothing hung, it ran DB writes and the Bluetooth close on the UI thread. The comment in `StatsViewModel.disconnect` saying this ran "off the main thread" was wrong. |
| C5 | **Socket leaks.** (a) `start()` returned after a successful `connect()` when a stop had arrived meanwhile, without closing the socket. (b) A cancellation during `initializeAdapter`/`settleProtocol` (before `runLoop`'s `try`) skipped every `disconnect()`. (c) `connectSocket` rethrew a cancellation without closing the socket, while its detached connect thread could still succeed afterwards. | Open RFCOMM sockets that nothing owns stay open until GC or process death. A single-link clone keeps serving that dead link and refuses or ignores new connects **until it is power-cycled**. |
| C6 | `start()` was not serialized. Two concurrent calls (service re-arm, a fresh user start, an ACL auto-start) could both run `cancelAndJoin` on the same old job and then both `launch`. | Two run loops. The stale one is hidden by the generation token but still talks to the transport, which means two connect attempts against a single-link dongle. |
| C7 | `BluetoothAclReceiver` stopped logging on every `ACL_DISCONNECTED` for the target. For an SPP-only dongle the ACL link exists only while one of our sockets is open, so each failed socket variant made the ACL flap. | Our own connect stopped the service partway through and armed the start debounce against the retry. |
| C8 | `cancelDiscovery()` was never called before `socket.connect()`, and the next connect did not wait after a close. | Slower or failed RFCOMM connects. A clone refuses a reconnect made immediately after a close. |
| C9 | Init sent `ATZ` as the very first bytes. It gave no chance to end a half-received command or a protocol search left over from the previous session, and there was no retry or fallback. | `?` / `STOPPED` / garbage became `bad ATZ: …`. |
| C10 | A clean stop only closed the socket. It never sent `ATPC`. | The adapter could be left mid-search for the next session. |
| C11 | `settleProtocol` treated any reply containing `SEARCHING` as "not yet locked". A real ELM prints `SEARCHING...` **and** the data in the same reply. `UNABLE TO CONNECT` / `BUS INIT: ...ERROR` were accepted silently. | The settle loop ran pointlessly, and a failed search was never retried. |

### Most likely explanation of "only a replug fixes it" (hypothesis, medium-high confidence)

Two things combine:

1. **The phone keeps a stale RFCOMM link open** (C5, C6, and C1/C4 hangs). The clone does not
   release it. A new connect then fails, or connects to a link whose UART side is dead. With
   the old code that showed up as a blank reply, which was reported as `INIT TIMEOUT` (C3).
   Power-cycling the dongle drops the stale link, which matches the symptom exactly.
2. **The dongle is left in a bad state or answers late**, which the broken timeout reports as
   `INIT TIMEOUT` (C2, C9, C10). Plugging the dongle back in resets it.

This cannot be confirmed without a logcat capture from the car. No device was attached, so
nothing was tested on hardware. The new logging makes every step visible, and the new error
codes separate "late reply" (`INIT TIMEOUT`) from "dead link" (`INIT EOF` /
`INIT WRITE FAILED` / `INIT READ ERROR`).

### MAF replies missing in some samples (2/282)

A desync cannot occur any more: a hung exchange closes its link, and every exchange first
drains stray bytes, logging them as `ELM drained stale bytes: …`. If that line shows up next
to a missing MAF sample, a late reply was the cause. Otherwise the most likely cause is `NO DATA`
from ELM adaptive timing (`ATAT1` + `ATST64`) on this CAN ECU. That belongs to the data-sanity
stream. The raw reply is now in logcat (`ELM<< …`), so it can be checked directly.

## What changed (file by file)

- **`data/obd/ElmLink.kt` (new, pure JVM).** One open ELM byte stream with deadlines that
  actually fire.
  - `exchange(cmd, timeoutMs)`: the blocking write+read runs on a daemon IO thread while the
    caller suspends. On the deadline, or on cancellation of the caller, the link is **closed**,
    which is the only reliable way to unblock `BluetoothSocket.read()`. The caller gets `""`
    immediately. Exchanges are serialized, and stray bytes are drained and logged before each
    write.
  - `exchangeSoft(cmd, timeoutMs)`: a non-destructive exchange that polls `available()` and
    does **not** close on timeout. It is used for the bare-CR line clear and for reset commands,
    so a clone that swallows its `ATZ` reply keeps the socket. It returns the `>` when the
    prompt was seen, so a prompt-only reply is distinguishable from silence.
  - `lastFailure` (`TIMEOUT` / `WRITE_FAILED` / `EOF` / `READ_ERROR` / `LINK_CLOSED`) and
    `printable()`, which escapes CR/LF and control bytes for raw-reply logging.
- **`domain/obd/ElmLinkFailure.kt` (new).** The failure causes listed above.
- **`data/obd/ObdTransport.kt`.** Added `sendCommand(command, timeoutMs)`,
  `sendSoft(command, timeoutMs)` and `lastFailure`. All three have default implementations, so
  existing in-memory fakes, including other streams' test fakes, still compile. The contract is
  documented: `disconnect()` must never wait for a pending read or lock.
- **`data/obd/BluetoothClassicTransport.kt` (rewritten).**
  - Uses `ElmLink`. Removed the broken `mSocket` reflection, which also clears the lint
    warning.
  - **Single-flight connect per dongle address, process-wide.** Two transports can never open
    two RFCOMM links. `isConnectInFlight(address)` is exposed for the ACL receiver.
  - `cancelDiscovery()` runs before connecting. `SecurityException` is tolerated when
    BLUETOOTH_SCAN is not granted.
  - **Every socket that does not become the link is closed.** That covers a failed variant, a
    timeout, a cancellation, a stream-setup failure, and a `disconnect()` racing a successful
    connect.
  - **Waits `RFCOMM_RELEASE_MS` (1 s) after the last close** before any new socket connect,
    process-wide and per address.
  - `disconnect()` also aborts an in-flight connect: it closes the pending socket and uses an
    epoch check.
  - Tagged `FuelRoute` logs for each step: lock, discovery, each variant, why it failed, each
    socket close and why, the release wait, plus raw `ELM>>` / `ELM<<` traffic.
- **`data/obd/ObdEngine.kt`** (connect, init, stop, reconnect and lifecycle only. The body of
  the sample/bin/trip loop is unchanged).
  - **`start()` and `stop()` are serialized by a `Mutex`.** A start that a newer start has
    already superseded does nothing.
  - **`stop()` is now `suspend`** and bounded. It first gives the loop 1.5 s to exit by itself,
    which sends `ATPC`. It then cancels, which closes an in-flight `ElmLink` exchange. After
    2 s it **force-closes the transport**. After another 3 s it abandons the stuck job and logs
    it. It never blocks a thread.
  - `requestStop(): Job` is a fire-and-forget stop on the engine's application-lifetime scope,
    and it never cancels a `start()` issued after it. `clearIfIdle()` is a non-suspending
    replacement for the UI's `if (!isRunning) reset()`. `disconnect()` and `reset()` are now
    `suspend`.
  - An outer `try/finally` around the whole run closes the transport on **every** exit path
    (C5).
  - `closeTransport()` is a best-effort `ATPC` (800 ms) followed by `disconnect()`. It skips
    the close when a newer run has taken over the same transport object, so a late cleanup from
    an abandoned run cannot close the new run's socket. It is used in `runLoop`'s `finally`
    (a one-line change there).
  - **New init sequence:**
    1. A bare CR (soft, 2 s), then 200 ms of quiet time.
    2. `ATZ` → `ATZ` → `ATWS`, all soft, with a CR line clear between tries. Banners are accepted
       even with garbage or a stale `?` around them.
    3. If no banner came back, `ATD` answering `OK` is accepted as proof the adapter is alive.
    4. Configuration commands `ATE0 ATL0 ATS1 ATH0 ATAT1 ATSP0 ATST64`, each with a hard 2 s
       deadline. A `?` reply is logged but not fatal.

    If neither the CR nor the first reset gets a single byte back, init fails fast instead of
    trying every fallback.
  - **Reconnect once:** after an init failure the engine closes the socket fully, waits 1 s,
    reconnects and re-initializes once before it reports the error. This is the software
    version of the manual replug. The run-loop reconnect path uses the same helper.
  - **Specific error codes:** `INIT TIMEOUT`, `INIT WRITE FAILED`, `INIT EOF`,
    `INIT READ ERROR`, `INIT LINK CLOSED` and `bad ATZ: <reply>`.
  - **Protocol settle:** sends `0100` with a 20 s search deadline and classifies the reply
    (`LOCKED` / `NO_DATA` / `BUS_ERROR` / `NO_REPLY`). A bus error gets `ATPC`, a 500 ms pause
    and a retry, up to 3 tries. A locked protocol is logged with `ATDPN`.
  - The first engine reconnect attempt is always made, even if the ACL link already dropped,
    because our own socket close drops it for SPP-only dongles (`shouldAttemptReconnect`).
- **`domain/obd/ObdConnectionPolicy.kt`.**
  - New deadlines: init 2 s (was 600 ms), reset 5 s (was 3 s), poll 10 s, protocol search 20 s,
    line clear 2 s, `ATPC`-on-close 800 ms.
  - RFCOMM release 1 s with `rfcommReleaseWaitMs`, stop budget 1.5 + 2 + 3 s, and
    `shouldRetryProtocolSearch`.
  - `initErrorCode(failure)`, `SESSION_OPEN_ATTEMPTS = 2`, `shouldAttemptReconnect`,
    `shouldIgnoreAclDisconnect`, and the new error codes.
- **`domain/obd/ElmProtocol.kt`** (init and banner parts only).
  - Added `CMD_RESET` / `CMD_WARM_START` / `CMD_SET_DEFAULTS` / `CMD_PROTOCOL_CLOSE` /
    `CMD_DESCRIBE_PROTOCOL_NUMBER`, plus `resetSequence` and `configurationCommands`.
    `initializationCommands` is kept as the nominal sequence.
  - `SearchOutcome` + `classifySearchReply`.
  - `isAcceptedAdapterBanner` ignores the echoed `ATZ`/`ATWS`. It accepts identity tokens
    (`ELM`, `STN`, `OBD`, `vX.Y`) despite surrounding noise, and rejects a bare `OK`, echo-only,
    `STOPPED` or `?`.
- **`service/ObdLoggingService.kt`.** `onDestroy` calls `engine.requestStop()` instead of the
  blocking `engine.stop()`.
- **`service/BluetoothAclReceiver.kt`.** Ignores `ACL_DISCONNECTED` while our own connect is in
  flight (`BluetoothClassicTransport.isConnectInFlight`) or while the engine is `Connecting`.
  It injects `ObdEngine`.
- **`ui/stats/StatsViewModel.kt`** (connect wiring only). Uses `engine.clearIfIdle()`. The
  suspending `disconnect()` / `reset()` run inside the existing `viewModelScope.launch`, and the
  wrong comment is fixed.
- **`data/obd/FakeObdTransport.kt`, `SimulatedObdTransport.kt`.** Canned replies for
  `ATWS`, `ATD`, `ATPC` and `ATDPN`.
- **`res/values/strings.xml`** (appended at the end). Hebrew texts for the four new `INIT …`
  codes. They are **not wired yet**, because `StatsScreen.obdErrorText` belongs to the UI
  stream. Until they are wired the UI shows the raw code, and lint reports them as
  `UnusedResources` warnings.
- `BootReceiver`: no change was needed.

## How it was tested

`.\gradlew.bat testDebugUnitTest lintDebug assembleDebug` all pass: 425 tests, 0 failures, 0 lint
errors.

The new tests use a fake socket (`test/.../FakeElmDevice.kt`) whose `read()` blocks and
**ignores interrupts and coroutine cancellation**, exactly like `BluetoothSocket`. Only `close()`
releases it. `StreamObdTransport` runs the **production `ElmLink`** on top of that socket.

- `ElmLinkTest` (9 tests):
  - A reply is read up to the prompt.
  - A silent adapter: the deadline fires in under 2 s, the link closes, and the parked IO thread
    is released.
  - Cancelling the caller closes the link at once.
  - An external close unblocks a pending exchange.
  - EOF, a write failure and a closed link are classified correctly.
  - Stray bytes are drained.
  - A soft exchange keeps the link on silence and marks the prompt.
- `ObdEngineLifecycleTest` (10 tests, real `ObdEngine` with mocked DAOs):
  - A healthy adapter runs the full sequence: CR first, then `ATZ` before `ATE0`, then `0100`
    and `ATDPN`.
  - **A silent adapter hits the init deadline, reopens once, and reports `INIT TIMEOUT`** in
    under 8 s with every socket closed.
  - A hard timeout on `ATE0` is classified as `TIMEOUT` and recovered by the reopen.
  - A swallowed `ATZ` plus a garbage banner is tolerated without losing the socket.
  - `UNABLE TO CONNECT` leads to `ATPC` and a retry.
  - **A run-loop poll timeout closes the link, and the reconnect path recovers on a fresh
    socket.**
  - **`stop()` returns in under 4.5 s while a read is hung.**
  - **`stop()` never hangs, even with a transport that ignores cancellation entirely** (the
    force-close path).
  - `requestStop()` never cancels a later `start()`.
  - A clean stop sends `ATPC` last.
- `ObdLinkPolicyTest` (11 tests): banner tolerance, the reset sequence, search classification,
  the retry rules, the RFCOMM release wait, distinct init error codes, reconnect gating, and the
  stop budget.

## Residual risks

- **No hardware test.** The clone-specific behaviour (does a bare CR repeat the last command?
  how long does `ATZ` take? does the ACL drop on close?) is modelled, not observed.
- `exchangeSoft` relies on `BluetoothInputStream.available()`. If a phone's stack always reports
  0, soft resets time out. Init would then fall through to `INIT TIMEOUT` and the reopen, which
  is no worse than before. Normal polls use the blocking read.
- A bare CR on an idle ELM **repeats the previous command**. After this change that is `ATPC`,
  which is harmless. After a crash it could be a PID, which starts a protocol search that the
  following `ATZ` interrupts, possibly with a late `STOPPED`. That case is handled by the drain,
  the second `ATZ`, and banner tolerance.
- If a transport ignores `disconnect()`, a stuck run is abandoned in the background after about
  6.5 s. It cannot touch the new run's state or socket, but its thread is lost until the read
  ends.
- 10 s poll deadline: an ECU that stops answering mid-drive while the ELM also stops sending
  prompts is detected after about 10 s and then reconnected. That is slower than ideal, but it is
  bounded.
- The four new UI strings need a mapping in `StatsScreen.obdErrorText` (UI stream).

## How the user can verify in the car

1. Install the build. With the phone on USB or Wi-Fi debugging, run
   `adb logcat -s FuelRoute:* AndroidRuntime:E`.
2. Connect normally. The log should show, in order:
   - `connect …: begin`, `trying SECURE_RFCOMM`, `RFCOMM link up`
   - `ELM init: line clear (bare CR) -> …`, `ELM>> ATZ (soft …)`, then
     `ELM init: adapter banner ELM327 v1.5`
   - the configuration commands, `protocol search 1: LOCKED`, `protocol locked: ATDPN=A6`
     (CAN 11-bit/500k is expected on a 2008 Civic)
3. Tap disconnect. The UI must respond at once, and the log must show `ELM>> ATPC` followed by
   `OBD transport closed`.
4. **Reconnect immediately without touching the dongle.** It should connect. The log may show
   `waiting …ms for the dongle to release the previous RFCOMM link`.
5. Turn the ignition off with the dongle still plugged in, then reconnect later. There should be
   no replug needed.
6. If it still fails, save the log. The error line now names the cause:
   - `INIT TIMEOUT`: no reply.
   - `INIT EOF` / `INIT READ ERROR` / `INIT WRITE FAILED`: the link was dead.
   - `bad ATZ: …`: a garbage reply, shown in escaped form.

   The raw `ELM<<` lines show exactly what the dongle sent.
