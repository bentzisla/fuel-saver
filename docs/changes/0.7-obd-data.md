# 0.7 — OBD data integrity (stream: obd-data)

## Problem

1. **Bug A (user-reported):** the app showed hundreds or thousands of L/100 km — live (Stats
   dashboard, overlay, notification, Android Auto) and in trips, and the learned curve was
   contaminated.
2. **Bug B:** "reset learning", "adopt learned curve" and backup import were silently undone
   while an OBD session was logging.

## Root causes (with evidence)

### A1 — engine displacement typed in cc (primary cause, from the user's phone DB)
- `vehicle`: Honda CIVIC 2008, GASOLINE, `engineDisplacementL = 1800.0`.
  `VehicleViewModel.save` stored `displacement.toDoubleOrNull()` unvalidated.
- `obd_sample`, 16:xx session: 282 samples, MAF present in only 2, MAP+RPM+IAT in all →
  `FuelRateCalculator` fell back to speed-density with a 1800 **L** engine:
  rpm 1751 / MAP 27 kPa / IAT 44 °C → 2.18 L/h at 1.8 L, **2177 L/h** at 1800.
- `trip`: #18 4.37 km, 345.8 L in 4.7 min (7919 L/100 km); #19, #12 similar. Morning sessions
  with MAF in ~95% of samples were sane (~5 L/100 km).
- `speed_bin_stats`: bins 1-21 at 150-9000 L/100 km (bin 19: 8.5 km / 52.6 L).
- MAF was intermittently missing mid-drive (09h: 39/104 samples, 16h: 2/282), so the
  estimator switched MAF ↔ speed-density sample by sample.

### A2 — per-sample live L/100 km
`ObdEngine` computed `instantL100 = fuelRate / speed * 100` whenever speed > 1 km/h. Pulling away
at 2 km/h with 15-20 L/h gives 750-1000 L/100 km (reproduced by
`AbsurdConsumptionRegressionTest`). Speed is integer km/h and speed/fuel are polled
sequentially (up to ~9 commands per loop), so they are not even simultaneous. The Android Auto
dashboard repeated the same division on EMA-smoothed values with a 1 km/h threshold.

### A3 — parser accepted replies that were not the requested PID's
`PidParser.parseMode01Bytes` merged all lines, tokenized every 2 hex chars anywhere and took
the first `41 <pid>` pair *anywhere*, returning *all* following bytes:
- a late reply of another PID whose data contains `41 0D` was read as speed
  (`41 0C 41 0D 7E` → 126 km/h);
- two ECUs: bytes of both messages were concatenated (`41 5E 01` + `41 5E 01 90` → 16.05 L/h);
- `41 0D 3C <DATA ERROR`, `STOPPED`, `CAN ERROR` after data were accepted.

### A4 — sentinel / impossible values propagated
Speed 255 (`FF`), MAF 655.35 g/s (`FF FF`, ≈ 215 L/h), 5E 3276.75 L/h and MAF at RPM 0 went
straight into trips and bins. Only speed > 250 and negative rates were filtered in the
aggregator.

### A5 — short trips / tiny bins
`Trip.litersPer100Km` divided by any distance > 0.1 m; `LearnedCurve` used any bin with > 0.1 m.
A bin with a few metres and a pull-away's fuel is absurd, and interpolation spread it to
neighbouring speeds with the confidence weight of a *different* bin.

### A6 — demo sessions polluted the real vehicle
The simulated transport learned into the active vehicle's `speed_bin_stats` and persisted
`obd_sample` rows under its id (only trips were tagged `demo`).

### A7 — diesel via MAF
MAF / 14.5 (stoichiometric) overestimates a lean-running diesel several-fold (λ ≈ 1.2 at full
load, 3-6 at light load/idle). No lambda PID is polled, so there is no verifiable correction.

### B — absolute snapshot writes
`ObdEngine.runLoop` loaded `speed_bin_stats` into memory at session start and every 30 s / on
stop wrote the whole map back with `@Upsert`. Any reset/adopt/import during the session was
overwritten by the next flush (adopt → the copied curve came back as learned data → double
counted in the blend). `BackupRepository.mergeSpeedBins` was itself a read-modify-write.
Additionally, the final flush in `finally` ran in an already-cancelled coroutine after
`stop()`, so Room's suspend calls threw immediately and up to 30 s of bins plus the open trip
were lost.

## Changes, file by file

### domain
- `domain/obd/PidParser.kt` — new `messages(raw)`: splits by line, drops non-hex lines,
  strips `SEARCHING...`/`BUS INIT: ...OK` prefixes and ISO-TP `N:` indexes (frames joined);
  the whole reply is rejected on `STOPPED`, `DATA ERROR`, `RX ERROR`, `BUFFER FULL`,
  `CAN ERROR`, `BUS ERROR`, `BUS BUSY`, `FB ERROR`, `ERRxx`. `parseMode01Bytes(raw, pid,
  minDataBytes)` only accepts a message that *starts* with `41 <pid>`, first complete one wins.
  Limitation: header mode (ATH1) is not parsed (the app sets ATH0).
- `domain/obd/ElmProtocol.kt` — 2-byte PIDs request `minDataBytes = 2`.
- `domain/obd/SampleSanitizer.kt` (new) — nulls implausible fields: speed ∉ 0..250,
  rpm ∉ 0..10000, MAF > max(100, 150·L) g/s (450 unknown), 5E > max(40, 40·L) L/h (80 unknown),
  MAF/5E at RPM 0, temperatures/load/MAP/level outside range.
- `domain/learning/EngineDisplacement.kt` (new) — `> 20` ⇒ cc ÷ 1000; valid 0.6-8.0 L else
  `null` (speed-density disabled rather than guessed).
- `domain/learning/FuelRateCalculator.kt` — `estimate()` returns L/h + `FuelRateSource`
  (DIRECT / MAF / SPEED_DENSITY) + `learnable`; normalizes displacement; rejects results above
  `SampleSanitizer.maxFuelRateLph`. **Diesel decision:** MAF and speed-density estimates for
  diesel are still shown live and used for trip totals (marked by source) but are
  `learnable = false`, so they never enter the curve; 5E is learnable. Not invented: no lambda
  correction.
- `domain/learning/ObdSampleProcessor.kt` (new) — the per-sample pipeline shared by the engine
  and the offline rebuild: sanitize → estimate × refuel correction → **estimator stickiness**
  (once 5E/MAF answered, a missing reply reuses the last value for ≤ 3 s; after that the
  lower-priority estimate is used for trips/live only and not learned; a 60 s gap resets) →
  aggregator deltas → live window. RPM exactly 0 ⇒ 0 L/h.
- `domain/obd/LiveConsumption.kt` (new) — `LiveConsumptionWindow`: trapezoid integration of
  fuel and distance over 8 s; L/100 = Σfuel/Σdistance only while moving (enter ≥ 8 km/h, exit
  < 5 km/h) and with ≥ 15 m in the window; L/h otherwise; display cap 99.9; gap > 5 s resets.
- `domain/learning/SpeedBinAggregator.kt` — rejects non-finite speed/dt and rates above the
  engine bound; documents that the map holds deltas.
- `domain/learning/LearnedDataPlausibility.kt` (new) — read-time rules: bin avg rate ≤ engine
  max (idle ≤ 6 L/h); moving bin with ≥ 0.5 km: L/100 ≤ max(60, 6 L/h ÷ v); curve points need
  ≥ 0.5 km; trip avg rate ≤ max and L/100 ≤ 60 (for ≥ 0.5 km).
- `domain/learning/LearnedCurve.kt` — only plausible bins with ≥ 0.5 km become points
  (`points`, `excludedBins`); implausible idle rate → null. Stored rows are not modified.
- `domain/learning/LearnedDataRebuilder.kt` (new) — replays raw samples through
  `ObdSampleProcessor` to rebuild bins and re-integrate trip fuel (demo windows excluded, gaps
  > 5 s not integrated, counts speed-density samples); `LearnedDataRepairPlanner` decides what
  may change (see repair below).
- `domain/model/Trip.kt` — `litersPer100Km` null below 0.5 km or when implausible;
  `isFuelPlausible`.
- `domain/model/SpeedBinStats.kt` — `mergeSpeedBins(base, deltas)` for the live view.

### data
- `data/db/Daos.kt` — `SpeedBinDao` is now an abstract class: `addDeltas()` (`@Transaction`,
  `UPDATE … SET x = x + :dx` then `INSERT` if 0 rows — SQLite UPSERT needs API 30, minSdk is
  26), `overwrite()` (repair only), `deleteBin()`. `ObdSampleDao.pageForVehicle` (keyset on
  id) and `countBetween`; `TripDao.closedForVehicle`. **No schema change, no migration.**
- `data/obd/ObdEngine.kt` (poll-loop body and persistence only) — uses `ObdSampleProcessor`;
  keeps `binDeltas` + a DB snapshot for display; flush = `addDeltas` then re-read (deltas kept
  on failure, retried); final flush + trip close under `NonCancellable`; raw parsed samples are
  persisted (for rebuilds); simulated transport: no learning, no sample persistence;
  `instantL100` / `fuelRateLph` in `LiveObdState` are now the smoothed window values.
  The `PARSE` diagnostic still keys on the raw speed parse (reconnect logic unchanged).
- `data/backup/BackupRepository.kt` — `mergeSpeedBins` = one `addDeltas` call.
- `data/obd/LearnedDataRepair.kt` (new) + `FuelRouteApp` (1 line) — background repair at app
  start, see below.
- `data/vehicle/VehicleRepository.kt` — displacement normalized on every read/write and in the
  legacy bootstrap.
- `data/history/DriveHistoryRepository.kt` — a trip with impossible fuel shows no actual
  liters/cost (and is excluded from the accuracy MAPE) instead of an absurd number.

### ui / car (minimal call sites)
- `ui/vehicle/VehicleViewModel.kt` — `EngineDisplacement.parseLiters` on save (1800 → 1.8,
  invalid → empty). The field label is owned by the UI stream ("litres, e.g. 1.8").
- `ui/curve/CurveViewModel.kt` — plots `learned.points` (guarded) instead of raw bins.
- `car/DashboardScreen.kt` — uses `state.instantL100` (null ⇒ show L/h); no more own division.
- StatsScreen / overlay / notification: unchanged code; they read `instantL100` (now smoothed,
  `null` while crawling → they show "-"; Stats already shows L/h next to it).

## Data repair (`LearnedDataRepair`)
- Trigger (per vehicle, every app start, cheap when clean): stored displacement needs
  normalization, **or** an implausible bin, **or** an implausible closed real trip.
- Rebuild: streams the vehicle's raw `obd_sample` rows (90-day retention), excluding demo-trip
  windows, through the live pipeline with the normalized displacement.
- Plan (conservative):
  - implausible bin → replaced by its rebuilt value if plausible, else deleted;
  - implausible trip → `fuelL` re-integrated if samples cover ≥ 50% of its duration (scaled to
    the full duration), `actualCost = fuelL × pricePerLiterAtTrip`; otherwise left as-is (UI
    hides its L/100 and liters);
  - only when the displacement was wrong: also every bin the rebuild covers and every trip
    that contains speed-density samples (they can be inflated while still looking plausible);
  - plausible rows are otherwise never touched.
- Safety: before writing, every row to change is archived to
  `files/repairs/learned-data-<vehicle>-<time>.json` (old/new bins, old trips, new fuel); if the
  archive cannot be written nothing is changed. All writes (bins, trips, normalized
  displacement) happen in one Room transaction. Logged under tag `FuelRoute`.
- Idempotent: after the repair no trigger matches (unless an implausible trip had no samples,
  in which case it is re-checked each start — a cheap query, and no write happens).

  script: pull-away, sentinels, desync, truncated/multi-ECU/`<DATA ERROR`/SEARCHING/BUS INIT)
  and `fixtures/obd/civic-2008-speed-density.csv` (shape of the user's 16:xx session). Each test
  first reproduces the absurd pre-fix values (≥ 500 L/100 km; > 1000 L/100 km with 1800), then
  asserts the fixed pipeline stays sane and learns only plausible bins.
- `PidParserRobustnessTest`, `SampleSanitizerTest`, `LiveConsumptionWindowTest`,
  `EngineDisplacementTest` (incl. 2177 → 2.18 L/h), extended `FuelRateCalculatorTest`.
- `LearnedDataRepairTest` — guards and planner with the phone-DB numbers (bin 19 8.5 km /
  52.6 L, trip #18 4.37 km / 345.8 L).
- `SpeedBinDaoDeltaTest` — `FakeSpeedBinDao` runs the real `addDeltas`; reset / adopt / import

## Residual risks / not done
- Overlay and notification show "-" instead of L/h while crawling (their files belong to the
  link-reliability stream; `LiveObdState.fuelRateLph` is available for that).
- A few seconds of pre-reset deltas (≤ 30 s, not yet flushed when the user resets) land in the
  new, empty curve. Negligible; documented.
- The repair can only rebuild what the 90-day sample retention still holds; older data in an
  implausible bin is removed (archived). Stored samples are ~1 Hz, so rebuilt bins are a bit
  coarser than live ones. Samples of demo sessions recorded before this change are excluded
  only via demo-trip windows.
- Speed-density itself remains approximate (VE 0.85 assumed); with stickiness it is only learned
  when the car never answers MAF/5E in that session.
- Hybrids: samples with the engine off (RPM 0) are still excluded from learning (pre-existing).
- The trip still uses the true wall-clock dt (a slow loop over several seconds still counts);
  gaps > 2 s are already excluded from learning.
- ELM header mode (ATH1) replies are not parsed (the app always sends ATH0).

## How to verify on the car
1. Install; open the app once (the repair runs in the background). `adb logcat -s FuelRoute:*`
   should show `learned-data repair for vehicle …` then `learned-data repair done … bin(s)
   rebuilt …` for the Civic, and the vehicle's displacement should now read 1.8.
   The archive is under `/data/data/com.fuelroute/files/repairs/`.
2. My curve: no point above ~20 L/100 km; the history rows for trips #12/#18/#19 show a few
   decilitres (or "-" if no raw samples were left).
3. Drive: at a standstill the dashboard shows "-" L/100 and a small L/h (~0.6-1.2); pulling
   away it stays "-" until ~8 km/h, then settles to trip-computer-like values (< 100, usually
   5-30 while accelerating, 4-8 when cruising).
4. While logging, tap "reset learning" in My curve; after ≥ 30 s the curve must stay (nearly)
   empty — it no longer comes back.
